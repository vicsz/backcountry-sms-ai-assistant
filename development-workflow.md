# Development workflow

This document defines how to implement one repository spec at a time. It is a process contract,
not an executable script and does not authorize deployment, live provider calls, SMS sends, or
commits by itself. It also defines a cost-aware default: use the smallest capable model, keep
context bounded, avoid duplicate agent work, and reserve expensive checks for the final gate.

## Choose the work type

This workflow defines the common engineering lifecycle: bounded scope, review, validation,
live-check, and commit controls. New behavior starts from one bounded spec. Existing broken,
failing, or regressed behavior starts from
[`bug-fixing-workflow.md`](bug-fixing-workflow.md), which requires a tracked bug record and an
automated regression test before commit.

Use [`docs/environments.md`](docs/environments.md) as the source of truth for environment names.
Only call a target “production” when it is actually deployed for real traffic; a production CDK
configuration or future spec is not a production deployment. “Live verification” means explicit
verification against the deployed target for the change, which is currently the demo capture
stack.

This separation is intentional for both maintainability and demonstration: specs show how planned
capability is delivered, while bug records show evidence-led diagnosis, corrective change, and
proof that a known failure does not return. The project-local
`.codex/skills/bug-fixing-workflow/SKILL.md` provides automatic routing guidance; it does not replace
these repository rules or authorize side effects.

## Commit naming

Commit messages must begin with the tracked work identifier:

- Bug work: `BUG-#### -- concise fix description`.
- Spec work: `SPEC-<stage> -- concise implementation description`.
- Documentation or maintenance work without a bug or spec uses the repository's normal concise
  prefix.

Use the identifier from the bug record or selected spec, not a newly invented number. A commit may
reference more than one identifier only when the records explicitly share one bounded change.

## Start with one spec

Select one spec path and keep the work bounded to its scope, acceptance criteria, and explicit
non-goals. Do not implement multiple stages in one change. Before coding, identify whether the
change is documentation-only, offline-test-only, infrastructure-only, or runtime behavior.

Use a prompt in this form:

> Implement `specs/<stage>.md` according to the repository instructions. Keep scope limited to the
> spec. Add or update tests for its acceptance criteria. Do not deploy, send SMS, or commit.

Include the spec path, relevant files, acceptance criteria, and required validation in the prompt.
Do not replay the whole conversation or ask the agent to inspect unrelated stages. Ask for a
concise report containing changed files, checks run, failures, and remaining decisions.

Use a stable, descriptive role label in every delegated prompt. The label is for human
traceability; Codex may still display an autogenerated sidebar handle for the subagent. For this
repository, use `Backcountry Implementer` for the coding agent and `Backcountry Reviewer` for the
independent review agent. Include the label, spec path, owned files, and non-goals near the start of
the prompt.

## Agent roles

### Implementer

Use the least expensive model that fits the risk:

- Luna for documentation, specs, status updates, straightforward tests, and bounded bug fixes.
- Terra Medium only for CDK/IAM changes, security or data-retention decisions, multi-module
  refactors, complex orchestration, difficult debugging, or ambiguous architecture.

The implementer is a clean agent. It changes code, infrastructure, tests, and narrowly related
documentation. During iteration it runs the smallest relevant targeted checks. It does not
deploy, send live messages, or commit. The applicable final validation gate is run once by the
orchestrator after review and any focused fix.

The implementer prompt must begin with or clearly include:

```text
Agent role: Backcountry Implementer
Owned scope: <spec path and relevant files>
Non-goals: <explicit exclusions>
```

### Reviewer

The reviewer is a separate clean, read-only agent with no implementation-agent context. Use Luna for
ordinary code, test, and documentation changes. Use Terra only when the diff materially involves
CDK, IAM, data retention, security, or complex orchestration. It reviews the current diff against
the selected spec and checks acceptance criteria, edge-case coverage, regressions, privacy/IAM
boundaries, generated files, and unnecessary scope. It reports findings; it does not edit files.

The reviewer prompt must begin with or clearly include:

```text
Agent role: Backcountry Reviewer
Review scope: <spec path and current diff>
Non-goals: do not edit, deploy, send SMS, or commit
```

Default review budget:

1. One implementation agent.
2. One reviewer.
3. At most one focused fix pass followed by re-validation.

Do not spawn repeated fresh reviewers for minor wording or test-only corrections. Start another
review only when a fix materially changes behavior or the previous review found a substantive
blocker.

Do not spawn parallel agents for the same change. Parallel work is appropriate only for genuinely
independent deliverables with separate file and acceptance-criteria ownership. More agents do not
replace a bounded implementation/review loop.

### Orchestrator

The parent task coordinates the implementer and reviewer, resolves findings, runs final validation,
decides whether live verification is required, updates `STATUS.md`, and creates the commit. Only
the orchestrator commits.

## Verification sequence

During implementation, use targeted checks such as:

```text
.venv/bin/pytest tests/test_handler.py -k precedence
```

After the reviewer has completed and any focused fix is applied, the orchestrator classifies the
final diff and runs the applicable gate exactly once.

For documentation-only changes—Markdown/spec/status/workflow edits with no code, tests,
infrastructure, dependency, or runtime-configuration changes—run:

1. Inspect the final diff and repository status.
2. Run `git diff --check`.
3. Send the diff to the separate read-only reviewer for an independent documentation review;
   confirm links, status claims, scope, and acceptance criteria are internally consistent.
4. Record that Ruff, the full test suite, CDK synth, and live checks were intentionally skipped
   because the diff cannot affect runtime behavior.

For any change that touches code, tests, infrastructure, dependencies, or runtime configuration,
run the full validation sequence exactly once:

1. Inspect the diff and repository status.
2. Send the diff and spec to the independent reviewer.
3. Resolve reviewer findings with at most one focused fix pass.
4. Inspect the final diff and repository status again.
5. Run Ruff:

   ```text
   .venv/bin/ruff check .
   ```

6. Run the full unit suite:

   ```text
   .venv/bin/pytest
   ```

7. Run the infrastructure synthesis check with the project’s configured CDK command:

   ```text
   npx aws-cdk synth
   ```

The reviewer is read-only and does not repeat the full test or synthesis suite unless explicitly
needed to investigate a finding. Local shell commands are not a substitute for review. If a
subsequent implementation-affecting change is required after the applicable gate, rerun the
affected checks and then the applicable final gate before completion.

## Live verification gate

Live checks are opt-in and depend on the change:

- Documentation-only changes: no live check.
- Offline test/eval changes: no SMS check.
- Provider, Bedrock, Lambda, SNS, or SMS behavior changes: perform the smallest relevant live
  check after review against the applicable deployed environment. Record the environment, stack,
  delivery mode, external calls, and result in the relevant bug or spec record.
- Use the approved SSO profile and region. Never use credentials copied into the repository.
- Use public test inputs and avoid production or personal message content where possible.
- Inspect redacted logs/metrics/traces when the spec requires operational verification.

Live checks must never be hidden inside pre-commit hooks or ordinary unit-test runs.

## Completion and commit

Before committing, confirm:

- the selected spec’s acceptance criteria are satisfied;
- the applicable validation gate is complete: documentation review and `git diff --check` for
  documentation-only changes, or Ruff, full unit tests, and `cdk synth` for implementation-
  affecting changes;
- reviewer findings are resolved or explicitly documented;
- required live verification passed, or was correctly skipped;
- the implemented spec’s `Status` field is updated (for example, to `Complete` or a clearly
  documented partial state);
- `STATUS.md` describes the actual state, including completed controls, current release boundary,
  evidence state, and next actions;
- no credentials, phone numbers, account IDs, secrets, generated AWS configuration, or unintended
  artifacts are staged.

Commit only after these checks. Then select the next spec as a new work unit.

## Safe command surface

If convenience commands are added later, they should wrap lint, tests, and synthesis only. Commands
that deploy infrastructure, call live Bedrock/providers, or send SMS must remain explicit and
manually invoked.

## Skills and tools

Use the narrowest available capability for the task:

- repository implementation and tests: normal coding tools;
- AWS console inspection: browser/computer-use capability;
- live SMS acceptance: the Messages connector;
- documentation/spec editing: normal Markdown tools.

Skills and connectors are execution capabilities, not repository runtime dependencies. Do not add a
skill or connector merely to satisfy a checklist.

## Token and side-effect discipline

- Pass agents the spec path, relevant files, and acceptance criteria instead of replaying the full
  conversation.
- Give each delegated agent a stable descriptive role label in its prompt and require that label
  in its final report; treat the Codex sidebar name as an autogenerated UI handle, not as the
  agent's function.
- Prefer `fork_turns=none` or a small bounded context for new agents. Continue the same
  implementation task for small follow-ups instead of opening a fresh context.
- Keep routine tasks on Luna. Use Terra only when the risk or ambiguity justifies it; do not use
  model switching as a substitute for narrowing the task.
- Keep agent concurrency to one implementer and one reviewer by default. Avoid exploratory agents
  that duplicate repository inspection.
- Keep reports and requested diffs concise; do not request repeated code dumps or long narration.
- Keep live provider, Bedrock, deployment, and SMS checks explicit and run them once after review.
- Never place live calls, deployment, or SMS sends in hooks or ordinary tests.
